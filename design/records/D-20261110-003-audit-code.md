## 2. 条目详情

### C1 读档异常被当成「无存档」，空态立即覆盖真实存档

- **现象与证据**：src/storage/tauriStorage.ts:17-37 中 load() 的 catch 直接 return { state: null }——任何异常（EACCES / 文件被占用 / OneDrive 锁 / 磁盘错误）都退化为「无存档」。src/store/appStore.ts:620-626 收到 saved === null 时仅置 hydrated: true；随后 appStore.ts:693-700 立刻挂上全量订阅，任何一次状态变更（含跨天刷新后的 UI 状态）都会触发 persistState 覆盖磁盘真实存档。localStorage 适配器同样（adapter.ts:356-357）。
- **根因**：LoadResult 只有「有/无存档/需升级」三种态，把 IO 故障与文件不存在混为一谈。
- **影响**：杀软/备份软件瞬时占用 blockhabit.json、权限被改、磁盘错误时，应用启动显示空数据并在首次交互后**永久覆盖**用户全部习惯/打卡/建筑。这是本审计唯一「一次误判即全量丢失」的路径。
- **方案**：

```ts
// adapter.ts
export interface LoadResult {
  state: AppState | null
  needsUpgrade?: boolean
  loadFailed?: boolean   // 读取失败（IO/权限/占用），而非文件不存在
  detail?: string
}
// tauriStorage.load：把 exists 与 read 拆开
if (!(await exists(path))) return { state: null }
let raw: string
try { raw = await readTextFile(path) }
catch (e) { return { state: null, loadFailed: true, detail: String(e) } }
// appStore.initPersistence：与 needsUpgrade 同构，挂起持久化
if (res.loadFailed) { useAppStore.setState({ hydrated: true, loadFailed: true }); return }
```

  并在 App.tsx 显示非阻塞 toast（存档读取失败，已暂停自动保存以避免覆盖，请检查磁盘/权限后重启），设置页提供「重新读取」。
- **验收**：新增 src/store/persistence.loadfail.test.ts：mock adapter 返回 {state:null, loadFailed:true}，执行 checkIn 后断言 saveSpy 调用次数为 0；新增 src/storage/tauriStorage.test.ts mock plugin-fs 使 readTextFile reject，断言 loadFailed === true（见 C18）。
- **工作量**：M
- **依赖**：与 C18（测试基建）、C9（提示 UI）同批；必须排在 C2 之前。

### C2 保存无串行化 + 固定 tmp 名，并发写可破坏主档

- **现象与证据**：src/storage/tauriStorage.ts:47-56 使用固定临时文件名并在 rename 失败时回退直写主档：

```ts
const tmpPath = path + '.tmp'          // 固定 tmp 名
await writeTextFile(tmpPath, json)
try { await rename(tmpPath, path) }     // 失败回退 writeTextFile(path, json)（非原子）
```

  src/store/appStore.ts:651-679 的 lastSavePromise 只是覆盖赋值，没有串行队列（lastSavePromise = adapter.save(...).then(...).catch(...)，不等待上一笔）；而 requestFlushNow()（appStore.ts:132-134）在每个关键 action 末尾同步调用，因此「打卡 A → 立刻打卡 B」「打卡 → 导入」「打卡 → 托盘退出 flush」都会在上一笔写未落地时启动第二笔。
- **根因**：写盘缺少互斥/队列，且临时文件名不唯一，两笔写共享同一 tmp。
- **影响**：A 的 rename 可能发生在 B 尚未写完 tmp 时 → 主档拿到半截 JSON；Windows 上 rename 因占用失败时回退为**直接覆盖主档**（非原子）。与 C9 叠加形成「损坏 → 静默重置 → 再次覆盖」。
- **方案**：

```ts
// tauriStorage.ts：唯一 tmp 名
let tmpSeq = 0
const tmpPath = `${path}.${++tmpSeq}.tmp`
// appStore.ts：串行队列
let saveChain: Promise<void> = Promise.resolve()
function persistState(state: AppState): void {
  const payload = pickPersistedFields(state)
  saveChain = saveChain
    .then(() => adapter.save(payload))
    .then(() => { if (useAppStore.getState().saveError !== undefined) useAppStore.setState({ saveError: undefined }) })
    .catch(() => { if (useAppStore.getState().saveError === undefined) useAppStore.setState({ saveError: Date.now() }) })
  lastSavePromise = saveChain
}
```

  flushSave 的内存层去抖合并不变；forceFlush() 返回 saveChain，托盘退出握手自然等待全部在途写。
- **验收**：新增 src/store/persistence.queue.test.ts：mock adapter.save 用可控 deferred，连续两次 checkIn 后断言第二次 save 在第一次 resolve 之后才被调用（记录调用顺序数组）；tauriStorage.test.ts 断言两次 save 的 tmp 路径不同。手测：快速连点 10 次打卡后强杀进程，重启存档可解析且含全部打卡。
- **工作量**：S
- **依赖**：无；建议与 C1 一起做（同属持久化批次）。

### C3 counter 习惯递减再递增可重复掉块（刷块漏洞）

- **现象与证据**：src/store/appStore.ts:283-289

```ts
const prevValue = todayCheckIns.reduce((s, c) => s + (c.value ?? 0), 0)
const nextValue = prevValue + stepDelta
const reachedTarget = prevValue < targetValue && nextValue >= targetValue
const shouldAwardBlock = !isCounter || reachedTarget
```

  UI 的减号按钮把负增量也送进同一个 checkIn：src/components/HabitRow.tsx:179-185 中 handleStepCounter 在 if (delta < 0 && counterVal <= 0) return 之后仍调用 checkIn(habit.id, undefined, undefined, delta)。canCheckInHabit 对 counter 跳过 already 拦截（logic/checkin.ts:65-67），因此「达标 → 减一档 → 再加回来」每次都会重新满足 reachedTarget。
- **根因**：掉块判定用「跨阈值事件」而非「当日该习惯是否已掉过块」这一事实。
- **影响**：用户（或误触）可在数秒内无限产出积木，直接摧毁建造进度与全勤/连击语义；counter 打卡记录还会出现大量负值行（entry.value = stepDelta，appStore.ts:338）。
- **方案**：

```ts
const awardedToday = todayCheckIns.some((c) => c.placedBlockId)  // 当日该习惯已掉过块
const shouldAwardBlock = !isCounter
  ? true
  : (!awardedToday && prevValue < targetValue && nextValue >= targetValue)
// 负增量只改数值，不参与 reachedTarget 计算
const countsTowardTarget = stepDelta > 0
```
- **验收**：src/store/appStore.test.ts 新增「counter 达标 → 递减 → 递增不再掉第二块」：断言 builds.length 只增 1，且 checkInDay/全勤判定仍正确。
- **工作量**：S
- **依赖**：无。

### C5 WebDAV 仍走 WebView fetch，CORS/Rust HTTP 未落地

- **现象与证据**：src/sync/webdav.ts:99-106 全部请求走浏览器 fetch；src-tauri/src/lib.rs:96 的 invoke_handler 只有 update_tray / tray_menu / confirm_quit；src-tauri/Cargo.toml:20-28 无 http/reqwest 依赖。10·03 方案 §8.2 写明「WebDAV CORS：fetch 走 WebView 的本质限制仍在（批次三 Rust HTTP 解决）」，但 9·30 批次三未包含 Rust HTTP → 该前置依赖至今悬空。
- **根因**：同步层从未迁出 WebView 网络栈。
- **影响**：自建 WebDAV（NAS/Alist/Nextcloud）默认不返回 Access-Control-Allow-Origin 时，GET/PUT 一律被 CORS 拦截 → 用户只看到 network 错误；PROPFIND/MKCOL/If-Match 属非简单请求，还需服务端放行预检。多设备同步在真实环境大概率不可用。
- **方案**（建议 A）：A. 加 tauri-plugin-http 或 reqwest，在 Rust 提供 webdav_request(url, method, headers, body) 命令；webdav.ts 用 isTauri() ? invoke(...) : fetch(...) 双实现，浏览器端保留 fetch 降级，CSP 无需放宽。B. 若本轮不做，设置页与 README 明确「仅支持已配置 CORS 的 WebDAV」，并把错误码 network 细分为 cors（fetch 抛 TypeError 时提示），避免用户误判为密码错误。
- **验收**：mock invoke 单测断言 Tauri 分支不调用 fetch（vi.stubGlobal('fetch', spy) 不被调用）；真机 + 无 CORS 头的本地 WebDAV 手测同步成功（方案 A）。
- **工作量**：M（A）/ S（B 的提示与文档）
- **依赖**：Cargo.toml 依赖新增需人类批准；与 C24（CSP）同批决策。

### C6 导入/远端档校验缺口可致整树崩溃（getBlueprint throw / foundationNotes）

- **现象与证据**：adapter.ts:127 对 activeBlueprintId 只校验「非空字符串」；src/logic/blueprints/index.ts:60-63 的 getBlueprint 对未知 id 直接 throw；getBlueprint 在渲染路径上被无条件调用：src/pages/Build.tsx:17、Today.tsx:61、src/App.tsx:232，仓库无 ErrorBoundary（grep componentDidCatch 无命中）→ 白屏。另外 adapter.ts:308-311 对 foundationNotes 只判 object，值类型不校验；Build.tsx:228 直接渲染该值，FoundationNoteDialog.tsx:26 又以其作为 textarea value → 对象/数字触发 React 崩溃。触发源：SettingsDialog.tsx:143 导入、useSync.ts:77-79 + merge.ts:253（activeBlueprintId = local || remote || 'plant'，本地坏值原样保留）。
- **根因**：严格校验只覆盖「类型」，未覆盖「引用完整性/值域」。
- **影响**：一份手改/旧版/被截断的导入档或远端档可让应用在切页时白屏，用户无法自愈（除非再导入）。
- **方案**：

```ts
// adapter.ts validateState 追加
import { blueprintOrder } from '../logic/blueprints'
const KNOWN_BP = new Set(blueprintOrder)
if (!KNOWN_BP.has(v.activeBlueprintId)) return { ok: false, error: 'activeBlueprintId' }
if (v.foundationNotes !== undefined) {
  if (!isRecord(v.foundationNotes)) return { ok: false, error: 'foundationNotes' }
  for (const [k, val] of Object.entries(v.foundationNotes)) {
    if (!KNOWN_BP.has(k) || typeof val !== 'string' || val.length > 500) return { ok: false, error: 'foundationNotes' }
  }
}
```

- **验收**：useSync.test.ts 新增「两侧一致时 syncNow 不调用 PUT、不触发 importData」（mock fetch 计数 / spy store）。
- **工作量**：S
- **依赖**：C5 网络层改动前更易做。

### C33 index.html a11y / lang 初值

- **现象与证据**：index.html:2 为 <html lang="en">（中文默认用户首帧被标注英文，App.tsx:302-304 挂载后才改）；index.html:6 为 maximum-scale=1.0, user-scalable=no（禁止缩放，WCAG 1.4.4 风险）。

- **方案**：lang 改 zh-CN（或按 navigator.language 在 main.tsx 启动前写入）；去掉 maximum-scale/user-scalable（画布缩放手势已由 touchAction:none 接管）。
- **验收**：DevTools Elements 首帧 lang 正确；手动缩放可用。
- **工作量**：S
- **依赖**：若与移动端设计冲突交 UX 审计裁决。

### C34 缺少 lint/format 配置；visual-harness 未接线；单文件超 800 行

- **现象与证据**：package.json:6-14 无 lint/format script，仓库无 eslint/prettier/editorconfig 配置（glob 无命中）；scripts/visual-harness.ts 存在但无调用点；AGENTS.md §4 规定「单文件超过 800 行时，新增逻辑应拆到新文件」，实际 src/render/iso.ts **1024 行**、src/render/BuildScene.tsx **853 行**、src/components/ui.css >1179 行。
- **根因**：工程约束没有工具化，只有文档约定。
- **影响**：风格漂移与超长文件继续增长（iso.ts 已超 25%），后续改动风险与 review 成本上升；视觉工具闲置等于 C20 的资产浪费。

- **验收**：npm run lint 零错误；npm run visual 产出 PNG；iso.ts < 800 行且 npm test 全绿。
- **工作量**：M
- **依赖**：新增 devDependency 需批准；拆分文件需在无并发改动时进行。
