## 背景与问题

上一轮（D-20261110-016 / 020 / 040）已经把展台拖拽热路径零分配化、精灵缓存加 LRU 上限、主 chunk 分包，但缺少可复现的运行时数字：建造页落块动画期间、展台连续拖拽、从今日切到建造页的首次渲染，各有多少长帧？高分屏 canvas 的 DPR 上限是否合理？用户主观反馈的「卡顿」目前无法定位。

## 设计决定

先测量、后优化、再复测，且所有优化必须视觉零回归：

1. 用 agent-browser/CDP 在 dev 与生产预览两端采集：页面切换 long task、Build/Showcase 的 rAF 帧间隔（均值/P95/长帧比例）、连续 pointermove 的 JS 耗时、canvas 像素尺寸与 DPR、内存。
2. 只允许三类改动：① 减少每帧分配与重复计算（缓存/预计算/复用离屏 canvas）；② 事件与重绘节流（pointermove 合并到 rAF、避免无变化重绘）；③ 明确的 DPR 上限（若 3x/4x 屏显著拖慢且视觉不可辨）。
3. 每个改动前后用同一脚本复测，并在记录中给出数字；渲染输出用像素 diff 证明 0 差异（不接受「看起来一样」）。
4. 若测量证明现有实现已达标（≥55fps、无 >50ms 长任务），不改代码，只把基线写进记录，避免为优化而优化。

## 取舍与被否方案

- 否掉重写 WebGL / 引入渲染库：见 D-20261110-006 §6 的明确不做项；现有 2D 等距 + sprite 缓存的瓶颈不在 API。
- 否掉降低任何视觉质量（去掉阴影/凸点/植被）：AESTHETIC §6 规定性能不足先砍环境装饰，但本轮目标是先证明是否真的不足；未经测量就砍是破坏产品承诺。
- 否掉用 React 渲染循环替代 canvas：会引入更大的 diff 与不一样的像素结果。

## 影响面

- 仅 src/render/** 与构建配置；页面组件、i18n、数据模型不动。
- 产物：build/showcase 场景 chunk 体积与首帧时间；内存上限。
- 需要保留一份可复跑的测量脚本与报告（.tmp-perf/，作为证据，不提交产物目录）。

## 验收标准

1. 基线报告：改造前 build/showcase 的 FPS、P95 帧间隔、长帧数、切页耗时、canvas DPR 与像素尺寸、内存。
2. 每项优化有前后对比数字；若无优化，记录必须给出「达标，不改」的测量证据。
3. 像素级回归：建造页（0/3/24/190 块）与展台页（0/3 座）在四主题下与改造前逐像素 0 差异。
4. tsc / npm test / npm run design:check 通过；sprite cache 预算测试仍绿。
