# BlockHabit 设计中枢（Design Hub）

> **这是全项目唯一的设计入口。**
> 任何人——包括 AI 代理——在动手做任何**视觉 / 交互 / 美术 / 动效 / 文案 / 品牌**改动之前，**必须从这份文件开始读**。
> 每次设计完成后，**必须**把它写成 `design/records/` 下的一条记录，并登记到本文件的索引与 `design/index.json`。
> **禁止删除本目录下的任何记录。** 删除必须先走人工审核（见 §5）。

---

## 0. 60 秒上手

| 步骤 | 动作 | 命令 / 文件 |
|---|---|---|
| 1 | 读设计公理，确认你的改动不违反任何一条 | 本文件 §1 |
| 2 | 打开对应规范，把你要用的令牌/参数抄出来（不要自己发明数值） | `TOKENS.md` `ART.md` `SURFACES.md` `VOICE.md` |
| 3 | 查历史：这个问题以前设计过吗？被否过吗？ | `RECORDS.md` → `records/*.md` |
- [`REVIEW-QUEUE.md`](REVIEW-QUEUE.md) —— **待审记录与决策清单**（自审计实测 + 按审核成本分组，人工审核从这里开始）
| 4 | 设计并实现 | `src/**` |
| 5 | **写记录**：在 `records/` 新建一条，登记到 `RECORDS.md` 与 `index.json` | 见 §3 模板 |
| 6 | 自检 | `npm run design:check` |
| 7 | 人类审核把 `status` 改为 `approved` / `implemented` | 见 §4 状态机 |

> 顺序不能反：**先查后设计，先写记录再宣称完成。**

## 1. 设计公理（A1–A7，不可动摇）

改任何界面之前，逐条自问。**任何一条被违反，设计即被否决**，与技术实现无关。

### A1 黑白灰为骨，琥珀为魂 —— 点缀色纪律
- **含义**：整个产品的颜色预算只有两种：无彩度的黑白灰（由四套主题提供），与**唯一一个点缀色** `--accent`（默认琥珀 `#F5B301`，随主题切换）。
- **正例**：琥珀只出现在三处——① 已完成状态的勾 ② 今日新落积木的高亮 ③ 连击/全勤奖励块。其余一切（按钮、进度条、链接、图标、图表）都用 `--ink` / `--ink-2` / `--line`。
- **反例**：给"成功"加绿、给"危险"加红、给分类加彩色标签、给不点亮的格子加淡蓝。**进度条的绿、删除的红是既有例外，不得扩张**。
- **退化表现（会被用户看见）**：界面开始像后台管理面板；主题切换（燕麦/雾灰）时高亮色不跟随，出现"两种琥珀"。
- **落地检查**：`grep -rn "#f59e0b\|#F5B301" src/` 只允许出现在令牌推导处；见 `TOKENS.md` 的"越界清单"。

### A2 一切都是积木 —— 圆润几何与凸点
- **含义**：这个 App 里没有"网页元素"，只有积木。所有容器 = 圆角积木（`--r-sm/md/lg/pill`），所有按钮 = 可按压的积木块，所有图标 = 积木风 SVG，所有弹窗 = 一块浮起的积木板。
- **正例**：卡片 `--r-md` 14px、弹窗 `--r-lg` 20px、按钮胶囊、tab 是黑色胶囊滑块、时间步进器是方块按钮、提醒弹窗顶部积木依次落下咬合。
- **反例**：直角卡片、1px 硬边框、下划线链接、Material 涟漪、方角输入框。
- **退化表现**：出现"乐高玩具 + 网页表单"的缝合感，风格崩塌。

### A3 2.5D 等距是唯一的立体语言
- **含义**：产品里所有"立体"只能来自等距投影（iso）渲染出来的圆润积木立方体：顶面亮、左面中、右面暗、顶部凸点高光、地面接触阴影、虚线地基。**不允许** CSS 拟物 3D、不允许平面插画风、不允许用 emoji 代替积木。
- **正例**：建造页/展台页/积木掉落弹窗/图鉴缩略图全部共用 `iso.ts` 的同一套投影与着色。
- **反例**：给卡片加 box-shadow 制造"浮起"；用渐变假装立体；新增一套斜 45° 的假等距。
- **退化表现**：积木"浮"在地面上（无接触阴影）、墨黑主题积木黑上黑看不清、同一屏出现两种透视。

### A4 留白与 1px 细线，拒绝阴影堆叠
- **含义**：层级靠**留白、字号、线、以及黑白反转**表达，不靠阴影。全应用只允许极少量、极软的分层阴影（弹窗与胶囊按钮），不得层层叠。
- **正例**：卡片用 `--line` 1px 分隔；主按钮黑底白字（墨黑主题下白底黑字）；强调靠加粗与留白。
- **反例**：卡片套卡片套卡片、每层都加 shadow、用 3 种灰做卡片背景。

### A5 动效克制且有物理感
- **含义**：动效必须像"积木掉在桌上"：慢落 → 着地压扁 → 回弹。所有动画围绕这一条物理直觉展开；禁止无意义的淡入淡出与位移炫技。所有动画必须尊重 `prefers-reduced-motion`。
- **正例**：积木 240ms 缓动下落 + 落地压扁 + 回弹；正态分布的极短微交互（按压 0.97 缩放）。
- **反例**：整页转场、卡片飞行、连续循环的呼吸光晕、超过 500ms 的等待动画。

### A6 数据诚实优于视觉讨好
- **含义**：一个习惯"今天完成了吗"只能由规则判定（`habitMetOnDay`）决定，不能因为"有记录"就点亮绿勾。删掉一个数据必须同步删掉它带来的积木、连击与全勤。宁可显示"未完成"，也不做视觉上的假完成。
- **正例**：counter 习惯未达 targetValue 不亮勾；撤销打卡后积木回收、全勤重算；同步合并用墓碑而不是并集。
- **反例**：为了让页面"看起来更满"补假数据；空态伪造进度条。

### A7 本地优先，用户数据可带走
- **含义**：无账号、无后端、无遥测上传。数据落在用户机器上，随时可导出/导入 JSON。任何新功能都不得引入"必须联网才能用"的主路径。
- **正例**：Tauri `appDataDir/blockhabit.json` + 浏览器 localStorage 回退；手动导出/导入；WebDAV 是可选同步而非依赖。
- **反例**：把某功能放到云函数；把设置同步绑定到账号。

## 3. 标准流程：新增一条设计（5 步 + 模板）

**第 1 步 · 查**：`RECORDS.md` 全文搜索关键词。若已有记录且状态为 `superseded`/`deprecated` → 先读它，理解它为什么被换掉；不要重复踩坑。

**第 2 步 · 对齐**：确认改动落在 §1 哪几条公理之下，并把要用的令牌/参数**从 `TOKENS.md`/`ART.md` 抄出来**（禁止在代码里发明新数值）。

**第 3 步 · 记录先行**：先建记录文件（状态 `proposed`），写清"要解决什么、怎么解决、牺牲了什么"。**记录先于代码**——这是本规则的核心。

**第 4 步 · 实现**：改代码。改动必须能从记录里逐条追溯到。

**第 5 步 · 登记与自检**：在 `RECORDS.md` 的台账表加一行、在 `index.json` 加一条、跑 `npm run design:check`；然后交人类审核。

### 记录文件模板

```markdown
---
id: D-2026-11-10-001            # D-YYYYMMDD-NNN，全局唯一，不可复用
date: 2026-11-10                # 设计定稿日期
title: 一句话说明这次改了什么
status: proposed                # proposed | approved | implemented | superseded | deprecated | revoked
owner: <提出者>                  # 人类或 AI 的名字
surface: [today, build]         # 涉及界面表面（见 SURFACES.md），无则 []
axioms: [A1, A5]                # 这次设计落在哪几条公理之下
files: [src/theme.css]          # 实际改动文件
supersedes: []                  # 被本记录取代的旧记录 id
reviewer: pending               # 人工审核人；approved/implemented 必须填真实姓名
---

## 背景与问题
为什么现在要改？（用户可见症状 / 数据证据 / 历史记录链接）

## 设计决定
改什么，怎么改。必须引用 TOKENS/ART/SURFACES/VOICE 的具体条目或数值。

## 取舍与被否方案
考虑过但没有采用的方案，以及为什么放弃（这一节是最有价值的遗产）。

## 影响面
代码 / 品牌资产 / 文档 / 测试 / 需要人工走查的界面。

## 验收标准
可执行的验证：命令、测试名、截图对比、手测步骤。

## 变更履历
- 2026-11-10 created (owner)
```

## 4. 记录规范与状态机

```
proposed ──(人类审核)──> approved ──(实现并验证)──> implemented
   │                        │                        │
   │                        └────(被新设计取代)──────> superseded   （保留全文，不删除）
   └──(人类否决)──> revoked                                │
                                                           ▼
                                                     deprecated   （仍保留全文，仅不再推荐）
```

- **`approved` 及之后的状态只能由人类设置**。AI 只能写 `proposed`，并等待人类审核。
- 记录 **append-only**：已存在的记录**只允许**改两件事——`status` 与 `变更履历`。正文一旦写定不再改写；改了主意就**新增一条**并让旧的 `superseded`。
- 一条记录对应一次"设计决策"，不是一次代码提交。多个小修补若同源，可合并进一条。
- 编号 `D-YYYYMMDD-NNN` 按当日顺序递增，**永不复用**（删除过的编号也不复用）。
- 重大设计（新页面、新主题、新美术语言、新核心机制）必须先有记录并 `approved` 才能开工。

## 5. 删除规则（**唯一铁律**）

> **设计记录是项目记忆。记忆不允许静默消失。**

1. **AI 禁止删除** `design/` 下任何文件、任何章节、任何表格行。没有例外。
2. 想淘汰一条设计 → 把 `status` 改成 `deprecated` 或 `superseded`（**内容全文保留**）。这不算删除。
3. 确实要物理删除（例如记录写错了、含敏感信息）：
   - 在 `APPROVALS.md` 追加一条 `pending` 申请：要删什么、为什么、替代方案是什么；
   - **人类**在申请行填写 `approved` + 姓名 + 日期 + 关联 commit；
   - 删除后由执行人把该行状态改为 `done`，并在原位置保留一行"已按 approval-XXX 删除"的墓碑说明。
4. 校验脚本 `npm run design:check` 会对比 git HEAD：**发现未审批的记录删除 → 直接失败**（退出码非 0）。
5. 同样的纪律适用于**设计性资产**：`design/logo/**`、`src/theme.css` 的令牌、`src/logic/blueprints/generators.ts` 的建筑数据、`src-tauri/icons/**`。删除或改名这些资产，必须先有记录 + 人工审核。
